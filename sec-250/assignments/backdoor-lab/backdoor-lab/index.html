Backdoor Lab

Objective:

In this activity, you will understand how APTs set up backdoors to maintain access (persistence) to compromised systems. It is important to understand how attackers are able to obtain a shell on a remote system since it is a common method of maintaining access and stealing data (exfiltration or exfil). netcat is a simple but powerful program for establishing connections. netcat derives its name from the linux command for typing the contents of files: cat (short for concatenate – join).

Scenario:

Two systems can directly communicate to each other on an arbitrary port (i.e. there's no firewall or other device preventing them from communicating directly to each other.) Bob is the victim and Eve is the attacker, so one of you will be Bob for the duration of the assignment and the other one Eve. When the first person is done, switch roles.

Instructions:

Part 1: Preparation

  1. Log in to your Kali Linux VM

  2. If you haven’t already done so, change your Kali hostname to kali01-<your first name>

  3. Important: Check if your VM can sudo apt update. If you get a signature verification error like the screenshot below. Run this command:

sudo wget https://archive.kali.org/archive-keyring.gpg -O /usr/share/keyrings/kali-archive-keyring.gpg
  • If you’re curious why check out this link: https://www.kali.org/blog/new-kali-archive-signing-key/
  1. sudo apt update && sudo apt upgrade -y

Part 2: Installing Auditd

Auditd is a user-space component of the Linux Auditing System. It collects and writes audit log file records to the disk. These records can then be viewed using ausearch or aureport.

  1. Install auditd: sudo apt install auditd audispd-plugins

  2. Enable and start auditd. Check that it’s running:

    1. sudo systemctl enable auditd
    2. sudo systemctl start auditd
      • When trying to start auditd i got this error:
      • I fixed this error by changing kali1 in /etc/hosts to kali01-gavin. It seems that hostnamectl did not update the file.
    3. sudo systemctl status auditd

  3. Log out and then log back in

  4. Check that logs are being written using ausearch: sudo ausearch -m USER_LOGIN -ts recent. You should be able to see the logs from you just logged in.

    6. -m: Lets you search for an event matching a given message type. I.e USER_LOGIN
    7. -ts: Specifies how far back you want to search for logs. You can use a specific timestamp or words such as today, boot, yesterday, recent, etc. In this case we use recent, which pulls events from the last 10 minutes.
    Example:

The next few steps will result in your rules file looking something like this. Make sure to verify your rules against this screenshot once you have created them.

  1. Rule #1: We’re going to add an audit rule that logs all executions of /bin/bash
    1. Auditctl rules from the command line get erased if you restart your system, so to maintain persistent rules, we are going to create a rules file.
      sudo nano /etc/audit/rules.d/netcat-lab.rules
    2. To your file add: -a always,exit -F arch=b64 -S execve -F path=/usr/bin/bash -k bash-from-nc
      1. -a always, exit specifies that the system should always log this event when the syscall exits.
      2. -F arch=b64 matches 64-bit syscalls.
      3. -S bind/connect are the network syscalls we are going to be matching.
      4. -k specifies the keys that we are going to use to search for these rules later.
  2. Rules #2 and #3: To the same file, we’re going to add two rules that logs system calls to bind and connect.
    1. Bind Rule: -a always,exit -F arch=b64 -S bind -k socket-bind
    2. Connect Rule: -a always,exit -F arch=b64 -S connect -k socket-connect
    3. Save file and restart audit using this command: sudo systemctl restart auditd)

Part 6: Logs

To see the results of the rules we created we need to use ausearch.

  1. To see the results of the /usr/bin/bash rule: sudo ausearch -k bash-from-nc -i | grep 8001
    1. -k lets us filter events by their key and -i puts the port information into human readable values.
  2. To see the results of the Bind rule: sudo ausearch -k socket-bind | grep 8001
  3. To see the results of the Connect rule: sudo ausearch -k socket-connect -i | grep 8001

Part 7: Reflection

  1. Deliverable 11: Answer the following questions based on your experience in this lab:

  • Explain, in your own words, how the nc -lvp 8001 listener and nc X.X.X.X 8001 client produced an interactive shell. Which side is executing the shell process in each variant?
    The nc -lvp 8001 command started listening for connections on port 8001. The nc X.X.X.X 8001 command connected to the listener's IP address on port 8001. This allowed whatever was typed on the client to be sent over to the listener. The listener side is the one that produces the shell, the client only connects to the listener.

  • What is the difference in behavior between nc -lvp 8001 and nc -lvp 8001 -e /bin/bash? Why does the -e option change the attacker's capabilities?
    The difference is that the first command will only receive from a client while the second command will send everything it receives into /bin/bash. The -e option changes the attackers capabilities because /bin/bash will execute everything that is given to it as if the user typed it into the terminal themselves.

  • Why does sending plain text (e.g., echo “password is 1337” > FakeEvidenceHere.txt) demonstrate persistence of command execution, and where is that file stored?
    Sending plain text demonstrates the ability to create and modify files with the same permissions of the current user on the system. By default the file will be created within whatever directory was the user's working directory at the time they started the net-cat listener.

  • How might an attacker escalate from this simple shell to long-term control? List at least three techniques (e.g., persistence mechanisms, privilege escalation, scheduling tasks).
    An attacker could escalate from this by:

  1. Putting a program script on the computer that runs on startup that will always re-open the net-cat listener
  2. Configure a cron job to run the nc -lvp 8001 command every few minutes
  3. Install a key-logger on the system to capture the administrator password.

  • Examine the ausearch output from your bash-from-nc rule. What specific information does the audit log capture about the bash execution? Identify at least 4 key fields (e.g., timestamp, user, process ID, parent process) and explain why each would be valuable to a security analyst.
    Some of the things it captures are the port number, timestamp, user ID, and process ID. Port number would be helpful because it tells you what port you left open that allowed the conenction to happen. Timestamp is valuable because it helps you cross refrence between other logs. User ID is helpful because it tells you the user that ran the command. The process ID is useful because you can use it to kill the process if it is still running.

  • Your audit rule captured the bash execution on port 8001. If an attacker used port 443 instead (HTTPS), would your current rules still detect the activity? Why or why not? How might you modify your audit rules to be more flexible?
    Yes, my current rules would have still captured the bash execution if the attacker was using port 443 because the only thing it is checking for is the execution of bash, it is not checking for specific ports.
